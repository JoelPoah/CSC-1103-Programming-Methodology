Prediction 1: Higher optimisation level = faster

Expected: both programs would run faster as the optimisation level goes up from O0 to O3.

Result: The prediction mostly held. The user-input version got faster at every level up to O2
(Laptop 1.00x -> 1.82x, Pi 1.00x -> 6.27x). O3 gave little or no extra gain over O2
(Laptop 2.03x, Pi 6.26x). The fixed version went from about 75 ms (Laptop) / 278 ms (Pi)
at O0 to under 100 ns at O2 and O3.

Reason: At O0 the compiler does almost no optimisation, so it reads and writes i and total
to memory on every loop. From O1 it keeps them in CPU registers and makes the loop
simpler, which saves a lot of time. O3's extra optimisations don't help much on a loop this simple.


Prediction 2: Fixed N would be faster than N entered by the user

Expected: the fixed version would be faster, because the compiler already knows the value of N.

Result: The prediction held at O2 and O3. The fixed version took under 100 ns, while the
user-input version still took about 42 ms (Laptop) and 450 ms (Pi). At O0 and O1 the two
versions were about the same speed on the Laptop.

Reason: When N is fixed, the compiler can work out the whole sum before the program runs
and just print the answer (5000000050000000 appears as a constant in the O2 assembly), so
the loop is removed. When N is entered by the user, the value is only known at runtime,
so the loop still has to run.

Note: On the Pi, the user-input version at O0 (about 2.82 s) was about 10x slower than the
fixed version at O0 (about 278 ms), even though both run the same loop. This was repeated
twice with the same result. The cause has not been confirmed yet.
