ANALYSIS:

1. Loop vs recursion at -O0 and -O1: the loop is much faster.
   The loop only adds a number and moves to the next one. Recursion has to make
   10,000 function calls, and every call saves a return address and a stack frame
   on the stack, then removes it again on the way back. That extra work makes
   recursion about 70x slower than the loop on the Laptop and about 2.9x slower on the Pi
   at -O0 (see point 5 for why the Laptop gap is so much bigger).

2. -O0 to -O1: the loop gets faster, but at -O1 it no longer adds anything.
   At -O0, the loop reads and writes i and total from memory every time, which takes
   0.47 ns per number on the Laptop and 2.67 ns on the Pi (question a: 0.455 and 2.78 ns).
   At -O1 the time drops (1.74x Laptop, 3.19x Pi), but not for the reason we expected.
   Because n = 10000 is fixed in the code, gcc already works out the sum at -O1. The
   assembly (gcc -O1 -S, both machines) has 50005000 as a constant passed to printf, and
   the timed part is only an empty loop that counts down from 10000:

       Pi (b_O1.s)                       Laptop (x86)
       mov  x0, 10000                    movl $10000, %eax
   .L11: subs x0, x0, #1    // n - 1     .L5: subq $1, %rax
         bne  .L11          // until 0        jne  .L5
       mov  x1, 1032                     movl $50005000, %edx   // the answer
       movk x1, 0x2fb, lsl 16  // x1 = 0x02FB0408 = 50005000

   gcc worked out the answer but left the empty loop behind; -O2 removes that too.
   So the -O1 loop time measures 10,000 passes of a 2-instruction loop, not 10,000
   additions. This is why the Pi -O1 result (0.84 ns per pass, about 2 clock cycles at
   2.4 GHz) does not match question a's -O1 loop (0.42 ns, 1 cycle), where n is entered by
   the user and the 4-instruction loop really adds every number (a_O1.s):
   .L16: add x19, x19, x0   // total += i
         add x0, x0, 1      // i++
         cmp x24, x0        // compare n with i
         bcs .L16           // repeat while i <= n
   Why the Pi's empty loop takes 2 cycles per pass instead of 1 is not confirmed. Question
   a's fixed-N version at -O1 is the same kind of empty loop, and on the Pi it runs
   100,000,000 passes at 1 cycle each (41.7 ms). So the Pi can run this loop at 1 cycle
   per pass, and the 2 cycles here are most likely a start-up effect of a run this short
   (8 us). (The Laptop's empty loop takes 0.27 ns per pass, the same as question a.)
   This is the "watch the optimiser" effect the brief warns about, already at -O1.
   Recursion is still 10,000 real function calls at -O1. On the Laptop most of the time
   is growing the stack (see point 5), which -O1 cannot avoid, so -O1 is about the same
   as -O0 (0.96x, within the noise). On the Pi, -O1 saves a little (1.21x). Two of its
   five -O1 runs took about twice as long (131-134 us); the median ignores these, which
   is why it is used instead of the average.

3. -O2 and -O3: both programs take almost no time.
   n = 10000 is fixed in the code, so the compiler works out the answer before the
   program runs: for the loop already at -O1 (point 2), for recursion only from -O2.
   The Laptop -O2 assembly contains 50005000 as a fixed number and has no loop and no
   call to counter. The program only prints the answer, so the times measure nothing.
   -O3 gives no extra gain because there is no work left to remove.

4. These tiny numbers are limited by the timer, not the code.
   The Laptop timer counts in steps of 100 ns, so results show only 0 or 100 ns.
   The Pi timer counts in steps of about 18.5 ns, which is why its results are
   37, 55-56 or 74 ns (2, 3 or 4 steps). They are lower than the earlier Pi runs
   (74-93 ns) because reading the clock also takes less time at 2.4 GHz than at 1.5 GHz.

5. Laptop vs Pi, and why recursion is so slow on the Laptop:
   The Laptop runs the loop about 5.7x faster than the Pi at -O0 (question a gives 6.1x),
   but the Pi runs recursion about 4.3x faster than the Laptop.

   Tested on the Laptop: a separate test program called counter(10000) three times in a
   row inside one process (-O0, pinned, 3 tries). The first call took 329-364 us, but the
   second and third took only 86-139 us. The work is the same each time, so about 70% of
   the first call is a one-time cost. The -O0 assembly shows each call uses 48 bytes of
   stack (8 return address + 8 saved rbp + 32 "shadow space" that Windows x64 always
   reserves), so 10,000 calls need about 480 KB, which is about 117 new 4 KB stack pages.
   Windows gives the program these pages one at a time as the recursion goes deeper
   (each one is a guard-page fault handled by the OS), and that is the one-time cost.
   Our program only calls counter once, so it always pays it.
   Once the stack has grown, a Laptop call takes about 9 ns (86 us / 10,000). A Pi call
   takes about 7.6 ns (76 us / 10,000) including any stack growth. ARM frames are smaller
   and the Pi 5 kernel uses larger pages, so the Pi needs far fewer new pages. The Pi part
   was not measured directly, so it is the likely cause, not a confirmed one.
